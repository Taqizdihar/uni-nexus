# Database

## The database is the source of truth

`uni-nexus_db` (local: MySQL on `127.0.0.1:3306` via Laragon) already has the intended
schema. This project treats that schema as authoritative and only ever **reads** it —
nothing in the app, its scripts, or its tests creates, drops, or force-resets tables.

**Never run**, against this database:

- `prisma migrate reset`
- `prisma db push --force-reset`
- `DROP DATABASE` / `DROP TABLE`

There is no `prisma/migrations` directory in this project and no migration workflow —
schema changes happen in MySQL directly (or via whatever process owns
`uni-nexus_db`), and this repository is re-pointed at the result.

## Prisma introspection

[apps/api/prisma/schema.prisma](../apps/api/prisma/schema.prisma) is a Prisma schema
generated by introspecting the live database. Two commands touch it:

- **`npm run db:generate`** (safe, no database access) — runs `prisma generate`, which
  reads the schema file already on disk and produces the typed Prisma client the API
  imports. Run this after `npm install` and any time you edit the schema file by hand.
- **`npm run db:pull`** (reads the database schema, does not write to it) — runs `prisma
  db pull`, which re-introspects MySQL and **rewrites**
  `apps/api/prisma/schema.prisma`, including relation names and field order.

Only run `db:pull` deliberately, when the live schema has actually changed, and review
the diff before committing it — introspection can rename relations Prisma inferred
differently than before, which would ripple into `repository.ts`'s use of
`Prisma.dmmf` and into `packages/shared/src/resources.ts` (see below). If the schema
hasn't changed, prefer verifying connectivity instead:

```bash
curl http://localhost:3000/api/health/ready
```

(or query `SELECT 1` directly) rather than re-pulling for no reason.

The Prisma client connects through `@prisma/adapter-mariadb`
([lib/prisma.ts](../apps/api/src/lib/prisma.ts)), parsing `DATABASE_URL` into discrete
host/port/user/password/database fields for the driver adapter.

## Resource metadata is generated separately

The admin UI's modules are **not** driven directly by the Prisma schema. They're driven
by [packages/shared/src/resources.ts](../packages/shared/src/resources.ts), produced by
[scripts/generate-resources.mjs](../scripts/generate-resources.mjs) from two read-only,
checked-in exports of the schema:

- [docs/schema-columns.tsv](schema-columns.tsv) — one row per column
  (`TABLE_NAME`, `COLUMN_NAME`, `COLUMN_TYPE`, `IS_NULLABLE`, `COLUMN_DEFAULT`,
  `COLUMN_KEY`, `EXTRA`).
- [docs/schema-relations.tsv](schema-relations.tsv) — one row per foreign key
  (`TABLE_NAME`, `COLUMN_NAME`, `REFERENCED_TABLE_NAME`, `REFERENCED_COLUMN_NAME`).

These two files must be preserved and kept in sync with the real schema; regenerating
`resources.ts` from stale TSVs would silently drift from the live database. The
generator script itself never writes to MySQL — it only transforms these two files
(plus a small hand-maintained table of titles/descriptions/status enums) into
`resources.ts`. Re-run it with `node scripts/generate-resources.mjs` after refreshing
the TSVs from a real schema export, and review the diff before committing — the
currently-committed `resources.ts` is a reviewed, intentional snapshot, not something to
regenerate reflexively.

The generator's `configs` array is an **allow-list**, not a denylist:
`repository.ts`'s `repository()` refuses any table not present in `resources`, so a
table simply never being added to `configs` is what keeps it out of the generic engine
— there is no separate "hide this" step. `users`, `roles`, `workspace_members`, and the
identity tables introspected alongside the account-approval work
(`system_bootstrap`, `pets`, `user_tags`, `user_profile_assets`) are deliberately never
added to `configs`; they're owned entirely by the purpose-built `auth`,
`user-management`, `team`, and `profile` modules (see [IDENTITY.md](IDENTITY.md)),
which is also why `schema-columns.tsv`/`schema-relations.tsv` were not refreshed when
those tables were introspected — nothing in `generate-resources.mjs` reads rows for
tables outside `configs`, so their absence from the TSVs has no effect.

## Workspace scoping

Almost every business table carries a `workspace_id` column, and every generic-resource
query is automatically scoped to `request.workspace.id`
([modules/resources/repository.ts](../apps/api/src/modules/resources/repository.ts)'s
`scopeFor`) — a user can never read or write another workspace's rows through the API,
regardless of what the frontend sends. A few tables intentionally break this pattern:

- **`customers`** has no `workspace_id` — it's a shared, company-wide directory by
  design (see the comment in `scopeFor`), not a per-workspace list.
- **Child tables without their own `workspace_id`** (e.g. `product_variants`,
  `quotation_items`, `qc_check_items`) are scoped through their parent's
  `workspace_id` instead — `scopeFor` walks the Prisma relation graph to find it, rather
  than trusting a client-supplied parent ID.

## Important business relationships

The core flow a request moves through, and the tables involved:

```text
customers ──▶ custom_requests ──▶ quotations ──▶ orders ──▶ production_jobs ──▶ print_jobs
                     │                 │                          │                 │
                     ▼                 ▼                          ▼                 ▼
              request_files/     quotation_items            qc_inspections    slicing_results
              request_notes                                       │           print_failures
                     │                                              ▼
                     ▼                                      order_packaging
              design_tasks ──▶ design_assets ──▶ products (via "create product from design")
```

- A **quotation** references the `custom_request` it was built from; converting an
  accepted quotation to an **order** (`POST /quotations/:id/convert`) copies its items
  into a new order and keeps both the `quotation_id` and `custom_request_id` on the
  order, inside one transaction, idempotently.
- A **production job** is planned per order item and is the hub `print_jobs`,
  `qc_inspections`, and (via the order) `order_packaging` all reference.
- **`material_usages`** deducts `filament_spools.remaining_weight_gram` atomically in
  the same transaction that records the usage — stock is never adjusted separately from
  the event that consumed it.
- Once a relation is set at create time (e.g. a print job's `production_job_id`), the
  generic resource service treats it as **immutable** — `service.ts`'s
  `relationalConsistency` rejects attempts to move a child record to a different parent
  after creation, on a fixed list of parent-key fields. Create a new record instead of
  re-parenting one.
- **`audit_logs`** references `workspace_id`/`user_id`/`entity_type`/`entity_id` and is
  written inside the same transaction as every create/update/status-change across every
  module (see [services/audit.ts](../apps/api/src/services/audit.ts)) — it is the
  system's single change history, not a per-module log.

## Quotation pricing snapshots

The live `quotation_items` schema records the pricing evidence used when a line was
calculated: `pricing_rule_id`, `material_id`, `billable_weight_gram`, rule name/type,
per-gram/minimum/design/finishing snapshots, `pricing_breakdown_json`, and
`pricing_calculated_at`. `pricing_rule_id` references `pricing_rules`; `material_id`
references `materials`. Those records are historical snapshots rather than live pricing
joins, so a future rule edit never reprices an existing quotation or converted order.

`quotations` is uniquely constrained by `(custom_request_id, revision_no)`. The
workflow revision endpoint relies on that constraint in addition to a transaction lock.
These manually applied database changes are represented in Prisma and the checked-in
schema metadata only; this repository does not create a Prisma migration or run a
database reset for them.
